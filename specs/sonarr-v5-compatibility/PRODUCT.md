# Sonarr v5 Compatibility

## Summary

A single remediator image should recover and clean up eligible completed downloads on either Sonarr v4 or v5. Operators keep the same remediator configuration, state and permissions when they upgrade the same Sonarr instance. Support for a v5 beta is reported as such until the stable build is verified.

## Behavior

1. The observer identifies the configured Sonarr instance automatically. The existing server URL (including a reverse-proxy base path) and API key are sufficient. There is no API-version setting, browser login, new port, mount, or healthcheck. Existing v4 deployments need only update the remediator image. Status continues to show the Sonarr **application** version. An unavailable, unauthenticated, or incompatible instance cannot receive a mutation; an outage can recover on a later scan. A successfully identified unsupported major remains unsupported.
2. Background processing, manual preview, and manual execution see the same full queue, including unknown-series items. A multi-episode download is still one job. Every known episode contributes to scope, competition, matching, and the manual report. An active item of unknown coverage still blocks mutations for which competition cannot be excluded. Incomplete or inconsistent required reads cannot be published as a successful scan or authorize a mutation.
3. Recovery uses only Sonarr's automatic preview for the selected download. It can import an acceptable missing episode or replace an existing file only with a permitted strict improvement. Multi-episode, season, and multi-season packs require complete, corroborated membership and the same whole-download safety checks; one missing or ambiguous match cannot be dropped to make an import pass. The service does not infer matches from titles, episode numbers, or metadata provider IDs. It does not override Sonarr's rejection or reinterpret an equal file as an upgrade.
4. Redundant, unusable, and other rejected downloads keep their existing cleanup permissions, scope, and wait rules. A verified permanent episode/folder mismatch or explicit Sonarr executable-file queue warning can still qualify for immediate generic cleanup. A similar warning about a different rejection is not interchangeable. Missing or unrecognized rejection data is not proof of unusability, redundancy, or immediate cleanup authority. Generic rejected cleanup still never blocklists or starts a search.
5. An approved removal targets the whole tracked download, not individual episodes. It removes the item and data through Sonarr and blocklists only when the existing unusable-download policy permits it. It never triggers an implicit replacement search. If explicit replacement search is enabled, verified unusable removal can lead to a separate search for still-missing, monitored episodes that have no competing download.
6. Acknowledgement is not proof that an import or cleanup succeeded. Correlated history plus current episode-file evidence verifies imports; the complete queue and, when required, correlated failure and blocklist evidence verify cleanup. A replacement search is verified as submitted, not as having found a release. Partial, missing, or contradictory evidence keeps the corresponding work protected. A lost or ambiguous mutation response is never replayed through another route.
7. An in-place same-instance v4-to-v5 upgrade keeps wait progress, budgets, recorded work, manual receipts, and protection for pending and uncertain effects. Stop the observer during the Sonarr upgrade and resume it after Sonarr refreshes its queue. New or changed episode membership is evaluated afresh. If an older attempt can no longer be correlated to the same Sonarr records, keep its protection; do not start over by deleting state or guessing a match.
8. Existing dry-run defaults, manual preview isolation, manual execution permissions, wait override semantics, mutation limits, and queue/episode rechecks apply to both majors. No production Sonarr, downloader or library is modified to prove compatibility.
